### 🧱 2. Modelo OSI (lo justo y necesario)

#### ¿Qué es el modelo OSI?
- El Modelo OSI *(Open Systems Interconnection)* es un estándar universal que define los 7 pasos que siguen los datos para viajar de un dispositivo a otro. Piensa en él como un lenguaje común para que computadoras de diferentes marcas y tecnologías puedan entenderse.

#### ¿Para qué sirve?
- Para organizar el caos. Al dividir la comunicación en capas, si algo falla, sabemos exactamente dónde mirar: ¿Se rompió el cable? Fallo en la Capa 1 (Física). ¿La contraseña de la web está mal? Fallo en la Capa 7 (Aplicación).

| Capa | Nombre | ¿Qué hace? (simple) |
| --- | --- | --- |
| 1 | Física | Los cables, señales eléctricas o Wi-Fi.|
| 2 | Enlace | Conecta un dispositivo con el siguiente. |
| 3 | Red | Decide la mejor ruta (aquí viven las IP). |
| 4 | Transporte | Divide los datos en pedazos y revisa errores. |
| 5 | Sesión | Mantiene la conexión abierta y la cierra|
| 6 | Presentación | Traduce los datos (formato, cifrado). |
| 7 | Aplicación | Donde el usuario interactúa. |

### 🌐 3. DNS (lo que usas todos los días)

#### ¿Qué es DNS?
- El DNS *(Domain Name System)* es un sistema que traduce los nombres de las páginas web que tú escribes (como `google.com`) en las direcciones numéricas que las computadoras entienden (como `142.250.190.46`).

#### ¿Por qué no usamos IP directamente?
- Aunque técnicamente podrías escribir la IP en el navegador y entraría igual, no lo hacemos por tres razones:

    - Memoria humana: Es mucho más fácil recordar youtube.com que una cadena de números como `172.217.17.14`.
    - Flexibilidad (IPs dinámicas): Las empresas a veces cambian de servidor o de proveedor. Si Facebook cambia su dirección IP mañana, tú seguirías entrando por `facebook.com`.
    - Carga y escalabilidad: Un solo nombre (como `google.com`) puede estar asociado a cientos de direcciones IP en todo el mundo.

#### ¿Qué pasa cuando escribes `google.com` en el navegador?

- **Usuario**: Tú abres el navegador y escribes `google.com`. Tu computadora no sabe qué es eso, solo entiende números. Así que lanza un grito de auxilio a la red.
- **DNS (La Agenda)**: Tu solicitud llega al Servidor DNS. Es una base de datos gigante que asocia nombres con números. Tú preguntas: "¿Dónde vive `google.com`?". El DNS responde: "Vive en la dirección `142.250.190.46`".
- **IP (La Dirección)**: Ahora que tu navegador tiene la IP, ya sabe a qué puerta tocar. La IP es la dirección exacta del edificio (servidor) donde están guardados los archivos de Google. Tu computadora empaqueta tu solicitud y la envía a través de los cables de internet apuntando a ese número.
- **Servidor (El Anfitrión)**: La solicitud llega al Servidor de Google. Este recibe tu mensaje ("Hola, quiero ver tu página"), busca los archivos necesarios (el logo, la barra de búsqueda, los botones) y te los envía de vuelta en pequeños paquetes de datos.

👉 Flujo esperado:

**Usuario → DNS → IP → servidor**

En Resumen:
- **Usuario**: Escribe el nombre fácil de recordar (`google.com`).
- **DNS**: Traduce ese nombre a un número que la máquina entienda.
- **IP**: Es el "mapa" que guía los datos hasta el destino correcto.
- **Servidor**: Entrega la página web para que aparezca en tu pantalla.

### 🧩 4. Subnets (nivel básico pero clave)

#### ¿Qué es una subred?
- En términos simples, una subred es una división lógica de una red más grande. Imagina que una red es una empresa completa que ocupa todo un edificio. Una subred sería cada departamento (Contabilidad, Marketing, Sistemas) que tiene su propio espacio delimitado dentro de ese mismo edificio.

#### ¿Para qué sirve?
- Sirve principalmente para organizar y segmentar el tráfico de datos. En lugar de que todos los dispositivos de una empresa estén en una sola "bolsa" gigante gritándose mensajes unos a otros, los agrupamos para que la comunicación sea más ordenada.

#### ¿Por qué dividir redes?
- Dividir una red grande en trozos pequeños (subredes) se hace por tres razones críticas:

    - **Mejor Rendimiento**: Reduce el "ruido" o tráfico innecesario. En redes, hay mensajes llamados broadcast que se envían a todos. Si la red es gigante, hay tanto ruido que se vuelve lenta. Al dividirla, el ruido se queda atrapado solo en su pequeña sección.
    - **Mayor Seguridad**: Puedes aislar equipos. Por ejemplo, puedes crear una subred para "Invitados" (solo internet) y otra para "Servidores" (datos sensibles). Así, un invitado no tiene forma de entrar a ver los servidores.
    - **Gestión de Direcciones**: Permite aprovechar mejor las direcciones IP disponibles y hace que sea mucho más fácil encontrar fallos (si falla la subred de Ventas, ya sabes exactamente dónde buscar el cable suelto).

#### 👉 Ejemplo developer: Red local vs red en cloud

Para un desarrollador, la diferencia no es solo dónde están los cables, sino quién tiene el control y cómo se "invoca" la infraestructura. Aquí la comparativa directa:

- **Red Local (On-Premise)**: Es tu red "física". Los servidores, routers y cables están en tu oficina o en tu casa.

    - **Tú eres el dueño del hardware**: Si un switch se quema, te toca ir a comprar otro.
    - **Configuración manual**: Entras al router por cable o consola para abrir puertos o crear subredes.
    - **Latencia**: Casi inexistente (estás al lado del servidor).
    - **Escalabilidad** : Difícil. Si necesitas más capacidad de red, tienes que comprar más equipo físico.

- **Red en Cloud (VPC - Virtual Private Cloud)**: Es una red definida por software. Estás alquilando una sección aislada de los centros de datos de gigantes como AWS, Google o Azure.

    - **Todo es API o Consola**: No tocas cables. Creas subredes, firewalls y rutas haciendo clics o escribiendo código (Infrastructure as Code).
    - **Abstracción total**: No te importa qué marca es el router. Tú solo defines "quiero que este servidor se hable con este otro".
    - **Escalabilidad**: Infinita y al instante. Si necesitas 100 subredes nuevas, las tienes en segundos.
    - **Conectividad**: Está diseñada para Internet. Expone una base de datos al mundo en un clic (aunque peligroso).

| Característica | Red Local | Red en Cloud (VPC) |
| --- | --- | --- |
| **Implementación** | Compras cables y racks. | Escribes un archivo YAML o Terraform. |
| **Costo** | Gasto inicial alto (CapEx). | Pagas por lo que usas (OpEx). |
| **Mantenimiento** | Limpiar polvo y cambiar cables. | Configurar permisos y seguridad. |
| **Seguridad** | Física (llave en el rack). | Lógica (Grupos de Seguridad / IAM). |

### 💻 5. Conexión directa con desarrollo (CRÍTICO)

Lo que pasa con tu app si:
 
### No encuentra el servidor (Problema de IP / Ruta)

**¿Que pasa?**: Ya tienes la IP (ej. `192.168.1.50`), pero cuando tu app intenta enviar los paquetes de datos, "se pierden por el camino".

- **Relación con IP y Red**: La IP es la dirección física. Si la Red está mal configurada (un cable suelto, un router apagado o una mala ruta), el paquete de datos no sabe cómo llegar a ese destino.

- **Error típico en consola**: No route to host o Network is unreachable.

### No resuelve el dominio (Problema de DNS)

**¿Que pasa?**: Tu app intenta contactar a `api.servidor.com`, pero no obtiene una dirección numérica.

- **Relación con DNS**: El DNS es la "agenda de contactos" de internet. Tu app pregunta: "¿Cuál es el número de `https://www.google.com/url?sa=E&source=gmail&q=api.servidor.com`?" y el DNS responde: "No lo tengo en mi lista".

- **Error típico en consola**: `DNS_PROBE_FINISHED_NXDOMAIN` o `getaddrinfo ENOTFOUND`.

### No puede conectarse (Problema de Firewall / Puerto / Servicio) 

**¿Que pasa?**: Tu app llega al servidor (la IP es correcta y el camino está despejado), pero el servidor dice: "No te dejo pasar" o simplemente te ignora.

- **Relación con Red (Seguridad)**: Aquí entran los Firewalls o los Security Groups (en la nube). El servidor está ahí, pero tiene "la puerta cerrada" (el puerto, por ejemplo, el 80 o 443, no está abierto para ti). También puede ser que el servicio (tu API) esté apagado.

- **Error típico en consola**: `ECONNREFUSED` (Puerta cerrada) o `ETIMEDOUT` (Te ignoraron hasta que te cansaste de esperar).

### 🚨 6. Problemas reales (debugging)

🐛 Tabla ¿Qué significan estos errores?:
| Error	| Traducción Humana	| El problema está en... |
|---|---|---|
| `DNS not found` | "No sé quién es ese." | **El Nombre**. El sistema no puede traducir la URL (`https://www.google.com/search?q=google.com`) en una IP. |
| `Host unreachable` | "Sé quién es, pero no llego." | **La Ruta**. Tienes la IP, pero el camino en la red está cortado o no existe. |
| `Network error` | "Ni siquiera pude salir." | **La Conexión Local**. Suele ser un fallo genérico: no tienes internet, el cable está desconectado o el Wi-Fi falló. |

**¿Qué revisarías primero como developer?**

1. **¿Tengo internet yo? (Local)**: Abre el navegador y entra a cualquier sitio. Si nada carga, es tu `Network Error`.

2. **¿Escribí bien la URL? (DNS)**: Un punto de más o una letra mal y tendrás un DNS not found. Usa el comando `nslookup mi-api.com` para ver si resuelve la IP.

3. **¿El servidor responde "vida"? (IP/Ruta)**: Usa el comando ping [IP-del-servidor]. Si sale "`Time out`" o "`Unreachable`", hay un problema de red entre tú y el servidor.

4. **¿La puerta está abierta? (Puerto/Firewall)**: Si el ping funciona pero tu app no, el servidor te está bloqueando. Usa `curl -v http://mi-api.com:8080`. Si dice `Connection refused`, el puerto está cerrado.

### 🌍 7. Caso práctico real

**Escenario**: “Tu aplicación está deployada, pero nadie puede acceder”

La respuesta corta es: **Podría ser cualquiera de las tres**, pero se descartan siguiendo un orden lógico (de afuera hacia adentro).

1. **¿Es problema de DNS?**
Sabrás que es DNS si:

    - Al escribir la URL (`www.myapp.com`) el navegador dice "No se pudo encontrar la dirección IP".

    - La prueba de fuego: Si intentas entrar usando la IP directa del servidor (ej. `http://1.2.3.4`) y la app SÍ carga, entonces el problema es 100% el DNS. Tu "agenda" no está asociando el nombre con el número.

2. **¿Es problema de Red?**
Sabrás que es Red si:

    - Intentas entrar por IP y por nombre, y en ambos casos obtienes un "`Connection Timed Out`" (el navegador se queda cargando eternamente hasta que se rinde).

    - **Culpable común**: El Firewall o los Security Groups (en la nube). Tienes el servidor encendido, pero no has abierto el "agujero" (puerto 80 o 443) para que el tráfico de internet entre. La red está bloqueando el paso.

3. **¿Es problema de Configuración?**
Sabrás que es Configuración si:

    - Recibes un código de error específico del servidor, como un `502 Bad Gateway`, `503 Service Unavailable` o un tajante `Connection Refused`.

    - Aquí el tráfico SÍ llegó al servidor, pero tu software no sabe qué hacer con él.

    - **Culpable común**: Tu app está corriendo en el puerto 3000, pero tu servidor web (Nginx/Apache) está buscando en el puerto 80. O simplemente se te olvidó darle a "`Start`" al servicio.

| Si ves este síntoma... | El culpable es... | Lo que debes revisar: |
|---|---|---|
`DNS_PROBE_FINISHED_NXDOMAIN` | **DNS** | Los registros A o CNAME en tu proveedor de dominio. |
`Timed Out` (Carga infinita) | **Red** | Reglas de Firewall, Security Groups y que el servidor tenga IP pública. |
`Connection Refused` o `502/504` | **Configuración** | Logs de tu app, puerto de escucha y estado del servicio (systemctl/docker). |

## 🧠 BONUS (Nivel Bootcamp Pro)

- **¿Qué es un VPC en cloud?**: Es una red aislada lógicamente donde tú decides quién entra y quién sale.
- **¿Qué es una IP privada vs pública?**: Es la diferencia entre tu dirección de casa para el cartero y el número de habitación dentro de un hotel. La IP privada es gratis y segura; la pública suele costar dinero y es un objetivo para ataques.
- **¿Qué es un load balancer?**: Un Balanceador de Carga es el "semáforo" o "director de orquesta" de tu arquitectura. Recibe todo el tráfico que llega a tu IP pública y lo reparte entre varios servidores (nodos) para que ninguno se sature.
