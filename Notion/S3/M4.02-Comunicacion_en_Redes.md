### 🧩 1. Conceptos base

Completar tabla:

| Concepto | Definición simple | Nivel técnico breve | Ejemplo real |
| --- | --- | --- | --- |
| **TCP** | Es un cartero "perfeccionista": entrega todo en orden y confirma que recibiste cada carta. | Protocolo orientado a conexión que asegura que los datos lleguen sin errores y completos. | Descargar un archivo PDF o enviar un correo electrónico importante. |
| **UDP** | Es un cartero "veloz": lanza los paquetes rápido y no se detiene a revisar si los recogiste. | Protocolo sin conexión que prioriza la velocidad sobre la fiabilidad; no reenvía datos perdidos. | Una videollamada por Zoom o jugar una partida de un videojuego online. |
| **Puerto** | Son las "puertas" numeradas de un edificio (tu PC) para que cada dato sepa a qué cuarto entrar. | Identificador numérico (0-65535) que asigna el tráfico de red a una aplicación específica. | El puerto 80 para páginas web o el 25 para salida de correos. |
| **HTTP** | Es el "idioma oficial" que usan tu navegador y las páginas para entenderse entre sí. | Protocolo de transferencia de hipertexto basado en el modelo cliente-servidor (petición-respuesta). | Escribir "`www.google.com`" en Chrome para que el servidor te mande la web. |

### ⚙️ 2. TCP vs UDP (diferencia clave)

Responder:

1. **¿Cuál es la principal diferencia entre TCP y UDP?**

    La diferencia reside en la confirmación.
    - TCP establece una "conversación" previa entre los equipos para asegurarse de que ambos están listos.
    - UDP simplemente empieza a soltar la información sin preguntar si el otro lado está escuchando.
   
2. **¿Cuál es más confiable? ¿por qué?**

    El más confiable es **TCP**.
    - **¿Por qué?**: Porque tiene un sistema de "acuse de recibo". Si un pequeño paquete de datos se pierde en el camino, TCP se da cuenta, detiene todo y pide que se reenvíe ese fragmento. Al final, garantiza que la información llegue completa y en el orden correcto.

3. **¿Cuál es más rápido? ¿por qué?**

    El más rápido es **UDP**.
    - **¿Por qué?**: Porque no pierde tiempo revisando si los datos llegaron o pidiendo permiso para hablar. Simplemente envía el flujo de datos de forma continua. Es ideal cuando prefieres perder un "pixel" de imagen en una llamada antes que detener la transmisión por completo.

👉 Completar:

| Protocolo | Característica clave | Uso típico |
| --- | --- | --- |
| **TCP** | Orden y seguridad: Revisa errores y garantiza la entrega total. | Navegar por la web, leer correos o descargar apps. |
| **UDP** | Velocidad pura: Envía datos sin esperar confirmación del receptor. | Streaming en vivo, llamadas por WhatsApp o juegos online. |

### 🚪 3. Puertos (clave en desarrollo)

Responder:

1. **¿Qué es un puerto en una red?**:

    Imagina que tu dirección IP (tu conexión a Internet) es la dirección de un edificio de apartamentos. El puerto es el número de departamento específico.

    Sin puertos, el cartero sabría llegar a tu edificio, pero no sabría a quién entregarle el paquete. El puerto le dice a la información exactamente a qué "puerta" debe tocar dentro de tu computadora.
   
2. **¿Por qué una aplicación necesita un puerto?**

    Porque tu computadora corre muchas aplicaciones al mismo tiempo (Chrome, Spotify, Zoom, un videojuego).
    - Si llega un dato de un video, el puerto "avisa" que ese dato va para Zoom y no para tu correo.
    - Cada aplicación "escucha" en un puerto específico para que los datos no se mezclen. Es como tener extensiones telefónicas en una oficina: la línea es la misma, pero cada extensión va a un escritorio diferente.
    
3. **¿Qué significan estos puertos?**

| Puerto | Uso principal | ¿Qué hace realmente? |
|---|---|---|
| `80` | **HTTP** | Es el puerto para navegar por internet de forma básica y no segura (sin candadito). | 
| `443` | **HTTPS** | Es el puerto estándar para la navegación segura (con cifrado). Es el que usas para bancos y redes sociales. |
| `3000` | **Desarrollo** | Es el puerto "favorito" de los programadores para probar sus propias aplicaciones mientras las están creando. |
| `5432` | **PostgreSQL** | Es la puerta específica que usan las bases de datos de este tipo para recibir y enviar información. |

👉 Ejemplo developer:

- ¿Qué pasa cuando ejecutas:

```
npm run dev
```

**Resumen:**
| Acción | Lo que realmente pasa |
|---|---|
| Lectura | El sistema busca en `package.json` las instrucciones de encendido. | 
| Reserva | Se adueña de un Puerto (ej. `3000`) para recibir tus visitas. | 
| Emisión | Crea una dirección local (`localhost:3000`) que solo tú puedes ver. | 
| Escucha | Se queda esperando a que escribas algo nuevo para actualizarse. |

### 🌐 4. HTTP (HyperText Transfer Protocol)

Responder:

- **¿Qué es HTTP?**

Es un sistema de "Pregunta y Respuesta". HTTP es el protocolo (las reglas) que permite que pidas información a un servidor (como una imagen o un texto) y que este te la envíe de vuelta. Sin estas reglas, tu computadora y el servidor no sabrían cómo empezar a saludarse.

- **¿Cómo funciona una petición HTTP?**

Funciona en tres pasos muy sencillos:

1. **La Petición (Request)**: Tú escribes una dirección en el navegador. Tu computadora envía un mensaje al servidor diciendo: "Hola, ¿me das la página de inicio, por favor?".
    
2. **El Procesamiento**: El servidor recibe el mensaje, busca el archivo y verifica si tienes permiso para verlo.
    
3. **La Respuesta (Response)**: El servidor te envía un paquete con un código (como el famoso 200 OK) y el contenido de la web.


- **Los "Verbos" de HTTP**

| Verbo | Acción simple | Metáfora de la vida real |
|---|---|---|
| `GET` | Obtener información. | Leer el menú de un restaurante. |
| `POST` | Enviar información nueva. | Rellenar un formulario de registro y entregarlo. |
| `PUT` | Actualizar algo que ya existe. | Cambiar tu foto de perfil o editar un comentario. |
| `DELETE` | Borrar algo. | Eliminar una publicación de tu muro. |

👉 Explicar flujo:

```
Frontend → Request → Backend → Response → Frontend
```

El Flujo Explicado (Paso a Paso):

1. **Frontend (El Cliente/Mesa del Restaurante)**:

    - Eres tú interactuando con la pantalla (navegador web o app móvil).
    - **Ejemplo**: Ves un producto en una tienda online y haces clic en el botón "Añadir al carrito".

2. **Request (La Petición/El Mesero)**:

    - El Frontend prepara un mensaje digital (un Request HTTP, como vimos antes) que dice: "El usuario quiere añadir el producto ID '123' al carrito".
    - Este mensaje viaja por Internet (usando TCP/IP y Puertos) hacia el servidor.
    - **Ejemplo**: El mesero anota tu pedido y lo lleva a la cocina.

3. **Backend (El Servidor/La Cocina)**:

    - Es donde están las computadoras potentes, la lógica del negocio y la base de datos.
    - Recibe el Request, verifica si hay stock del producto en la base de datos, lo añade a tu carrito digital y guarda el cambio.
    - **Ejemplo**: El chef recibe la comanda, revisa los ingredientes, cocina el plato y lo pone en la bandeja.

4. **Response (La Respuesta/El Mesero de vuelta)**:

    - El Backend crea un nuevo mensaje (un Response HTTP) que dice: "¡Hecho! Producto añadido con éxito" (con un código `200 OK`) o "Error: No hay stock" (con un código `400`).
    - Este mensaje viaja de vuelta por Internet hacia tu dispositivo.
    - Ejemplo: El mesero te trae el plato o te dice que se acabó el ingrediente.

5. **Frontend (Actualización de Pantalla/Tú comiendo)**:

    - Tu navegador o app recibe el Response.
    - Si fue exitoso, actualiza la pantalla mostrando el icono del carrito con un número "1". Si falló, te muestra una alerta de "Sin stock".
    - **Ejemplo**: Tú recibes tu plato y empiezas a comer.

### 💻 5. Conexión directa con desarrollo (CRÍTICO)

Responder:

**¿Qué pasa cuando haces**:

```
fetch("http://localhost:3000/api")
```

Básicamente, le estás diciendo a tu navegador: "Oye, ve a la dirección de esta misma computadora (localhost), toca la puerta número 3000 y pide lo que haya en la carpeta /api".
El Navegador crea un sobre digital (un Request).

- Como no especificaste nada más, el navegador asume que quieres un GET (solo leer datos).
- El mensaje viaja internamente en tu PC hasta el servidor que tienes corriendo en ese puerto.
- El servidor responde y el fetch te devuelve una Promesa (un "vale por un dato") que se resolverá cuando la respuesta llegue.

**¿Qué protocolo se usa?**
Se usa **HTTP** (o **HTTPS** si fuera una web real con certificado de seguridad).
- A un nivel más profundo, para que ese **HTTP** sea confiable y no se pierdan datos, se apoya sobre el protocolo **TCP**.

**¿Qué puerto?**
El puerto es el **3000**.
- En el desarrollo web, el `3000` es como el "estándar por defecto" para servidores de prueba (como los de Node.js o React). Es la "puerta" que dejaste abierta al ejecutar tu comando de desarrollo (como el `npm run dev` que vimos antes).

**¿Qué tipo de comunicación?**
Es una comunicación de tipo **Cliente-Servidor** y es **Asíncrona**.

- **Cliente-Servidor**: Porque hay uno que pide (tu código JS) y otro que responde (tu API en el backend).
- **Asíncrona**: Esto es clave para un novato. Significa que tu programa **no se detiene a esperar** la respuesta. El código sigue corriendo y, cuando la API responde, el navegador te avisa para que manejes los datos. Es como pedir una pizza: haces la llamada y sigues viendo la tele; no te quedas parado junto al teléfono hasta que llegue el repartidor.

**Resumen Técnico**
| Elemento | Valor en ejemplo | Rol |
|---|---|---|
| Protocolo | `http://` | El lenguaje de la conversación. |
| Host | `localhost` | La dirección (tu propia máquina). |
| Puerto | `3000` | La puerta específica de entrada al servidor. |
| Path | `/api` | La sección específica que quieres consultar. |

### 🚨 6. Problemas reales (debugging)

Responder:
**¿Qué significan estos errores?**

| Error | Traducción al "humano" | Metáfora de la vida real |
|---|---|---|
| `Port already in use` | La puerta ya está ocupada. | Intentas entrar a una cabina telefónica, pero ya hay alguien adentro hablando. No caben dos. |
| `Connection refused` | Conexión rechazada. | Llegas a una casa, tocas el timbre, pero no hay nadie (o la puerta está tapiada). El lugar existe, pero nadie atiende. |
| `Timeout` | Tiempo agotado. | Pides una pizza y pasan 3 horas sin noticias. Te cansas de esperar y cancelas el pedido porque "expiró". |

**¿Qué revisarías como developer?**

Si te encuentras con estos mensajes en tu terminal, aquí tienes tu guía de supervivencia:

**🔴 Si ves: `Port already in use`**

- **El problema**: Tienes otra pestaña de la terminal abierta con el mismo proyecto corriendo, o un proceso viejo se quedó "trabado" ocupando ese puerto (ej. el `3000`).

    **Qué revisar:**
    - Cierra todas las terminales y vuelve a empezar.
    - Cambia el puerto en tu configuración (ej. usa el `3001`).
    - Usa un comando para "matar" al proceso que está ocupando ese puerto.

**🟡 Si ves: "Connection refused"**

- **El problema**: Tu Frontend está intentando hablar con el Backend, pero el Backend no está encendido.

    **Qué revisar:**
    - ¿Escribiste bien la dirección? (¿Es `localhost` o te equivocaste en una letra?).
    - ¿Encendiste el servidor del Backend (`npm run dev`)?
    - ¿El puerto que busca el Frontend es el mismo donde está escuchando el Backend?

**🔵 Si ves: "Timeout"**

- **El problema**: El mensaje llegó al servidor, pero este tardó demasiado en responder, o hay un "muro" (Firewall) que bloquea el camino.

    **Qué revisar:**
    - ¿Tienes internet estable?
    - ¿La base de datos es muy lenta o está caída?
    - ¿Pusiste una dirección IP que no existe o es privada?

### 🌍 7. Caso práctico real

Escenario:

> “Tu frontend no se conecta al backend”
> 

Responder:

**¿Puede ser problema de puerto? (Muy probable)**
Sí, y es la causa número uno.

- **El desajuste**: Tu backend puede estar escuchando en el puerto `5000`, pero tu frontend está configurado para llamar al `3000`. Es como si tus amigos te buscaran en el departamento 301 pero tú te mudaste al 501.
- **La traba**: El puerto está bloqueado por el firewall de tu computadora o ya está ocupado por otra aplicación, impidiendo que el backend se "estacione" ahí.

**¿Puede ser problema de protocolo? (Probable)**
Sí, especialmente por el tema de la seguridad.

- **HTTP vs HTTPS**: Si tu frontend está en una web segura (`https://`) e intenta llamar a un backend que solo usa `http://` (sin la S), el navegador bloqueará la conexión por seguridad. Se llama "Mixed Content error".
- **Escritura**: Un simple error de dedo escribiendo `htp://` en lugar de `http://` en el código del fetch hará que la petición nunca salga.

**¿Puede ser problema de red? (Posible)**
Sí, dependiendo de dónde estén "viviendo" tus aplicaciones.

- **Localhost vs IP**: Si estás probando tu app en el celular pero el backend está en tu PC, no puedes usar `localhost`. Tienes que usar la dirección IP real de tu computadora (ej. `192.168.1.15`).
- **CORS (El guardián de la red)**: Este es un problema de red/seguridad muy común. El servidor (backend) recibe la petición pero dice: "No conozco a este frontend, no le voy a responder". El navegador te mostrará un error de "CORS policy".

## 🧠 BONUS

Responder:

- **¿Qué es HTTPS?**: Es **HTTP + Candado**. Cifra los datos para que nadie pueda "espiarlos" mientras viajan por el Wi-Fi.
    - **Clave**: Si no hay `s`, los datos viajan en texto plano.
- **¿Qué es REST?**: Es la **guía de estilo** para organizar tu API. Dice que debes usar nombres de objetos y verbos HTTP claros.
    - **Mal (No es REST)**: `GET /obtenerTodosLosUsuarios`.
    - **Bien (Es REST)**: `GET /usuarios`
- **¿Qué es un endpoint?**: Es la **dirección exacta** a la que el Frontend le pide algo al Backend.
    - **Ejemplo**: `https://api.tuweb.com/v1/productos`

| **HTTPS** | Protocolo Seguro | Protege contraseñas y tarjetas. |
| **REST** | Arquitectura/Reglas | Hace que tu código sea ordenado y profesional. |
| **Endpoint** | URL específica | Es el "botón" digital que el Frontend pulsa. |
